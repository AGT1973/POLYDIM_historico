### 💀 FALLO CRÍTICO 3: La Trampa Antipodal en `log_map` (Muerte Silenciosa del Gradiente)
**El Ataque Teórico:** El Whitebook (Sección 2.2) jura que el mapa de medio ángulo cordal es "suave en antípodas (Bug C4)".
**El Daño en el Código:** Mira qué pasa en `log_map` cuando $y = -x$ (antípoda).

**El Veredicto:** En el antípoda, la distancia es $\pi$, pero tu código devuelve el **vector cero**.

Si tu `log_map` devuelve cero en el antípoda, **el gradiente se anula**. El modelo dejará de aprender si dos representaciones se vuelven antipodales. Es un fallo catastrófico de aprendizaje.

**La Solución (Bulldog Fix):**

```python

@jax.jit
def log_map(x: jnp.ndarray, y: jnp.ndarray, tau_geom: float = 1e-12) -> jnp.ndarray:
    # ... (cálculo de theta, diff_norm, sum_norm igual que antes) ...
    
    proj = yu - GeodesicKernels.safe_dot(yu, xu, keepdims=True) * xu
    proj_norm = GeodesicKernels.safe_norm(proj, keepdims=True, eps=eps)
    
    is_antipodal = sum_norm < tau_geom
    
    # Fallback para antípodas: Generar un vector tangente ortogonal a xu
    # Usamos una máscara para seleccionar una dimensión que no sea cero en xu
    mask = jnp.abs(xu) < 0.5 
    # Si xu es casi cero en la dim 0, usamos el vector base e_0, sino e_1
    base_vec = jnp.where(mask[..., 0:1], jnp.eye(xu.shape[-1])[0], jnp.eye(xu.shape[-1])[1])
    # Proyectar base_vec al plano tangente de xu
    fallback_tangent = base_vec - GeodesicKernels.safe_dot(base_vec, xu, keepdims=True) * xu
    fallback_tangent = fallback_tangent / GeodesicKernels.safe_norm(fallback_tangent, keepdims=True, eps=eps)
    
    safe_proj_norm = jnp.where(proj_norm < eps, 1.0, proj_norm)
    u_tangent = proj / safe_proj_norm
    
    # Si es antípoda, usamos el fallback, sino el normal
    final_u = jnp.where(is_antipodal, fallback_tangent, u_tangent)
    log_normal = theta * final_u
    
    return jnp.where(theta < tau_geom, jnp.zeros_like(x), log_normal)
```

```python
@staticmethod
@partial(jax.jit, static_argnames=['max_iter'])
def cholesky_qr3(W: jnp.ndarray, max_iter: int = 3) -> jnp.ndarray:
    eps = jnp.finfo(W.dtype).eps
    K = W.shape[-1]
    I = jnp.eye(K, dtype=W.dtype)
    Q = W
    for _ in range(max_iter):
        G = jnp.einsum('...ji,...jk->...ik', Q, Q)
        trace_G = jnp.trace(G, axis1=-2, axis2=-1)[..., None, None]
        shift = jnp.maximum(eps, 11.0 * eps * trace_G / K) * I
        G_reg = G + shift
        L = jnp.linalg.cholesky(G_reg)
        
        # FIX BULLDOG: Resolver Q_new @ L^T = Q directamente.
        # left_side=False significa que resolvemos X @ A = B -> X = B @ A^-1
        # lower=True, transpose_a=True significa que A es L^T (triangular superior)
        Q = jax.lax.linalg.triangular_solve(
            L, Q, left_side=False, lower=True, transpose_a=True
        )
    return Q
```

```python
    @partial(jax.jit, static_argnames=['max_iter'])
    def cholesky_qr3(W: jnp.ndarray, max_iter: int = 3) -> jnp.ndarray:
```

#### 💀 FALLO NIVEL 4.1: El Asesino de Fusión XLA en `safe_norm` (Cuello de Botella de HBM)
**El Ataque:** Mira tu `safe_norm`.

**El Daño en el Silicio:** `jnp.max` es una **reducción global**. En XLA, cuando haces un `max` seguido de una división y luego un `sum`, el compilador **no puede fusionar** estas operaciones en un solo kernel de GPU. 
¿Qué pasa físicamente? XLA escribe el tensor `x` en la memoria HBM de la GPU, calcula el `max`, lo guarda, vuelve a leer `x` y el `max` para dividir, y vuelve a escribir. En $D = 1,000,000$, esto son **3 lecturas/escrituras de 8MB por vector**. En un `fori_loop` de Newton (5 iteraciones), estás estrangulando el ancho de banda de memoria (Memory Bandwidth Bound).
**La Solución SOTA:** Como activaste `jax_enable_x64 = True`, **no necesitas la escala `max`**. FP64 soporta valores hasta $10^{308}$. El overflow es imposible en vectores normalizados. Elimina el `max` y deja que XLA fusione todo en un solo kernel de norma L2.
```python

    @partial(jax.jit, static_argnames=['keepdims'])
    def safe_norm(x: jnp.ndarray, keepdims: bool = False, eps: float = 1e-12) -> jnp.ndarray:
        # FIX NIVEL 4: Norma L2 directa. XLA la fusionará en un solo kernel sin syncs de HBM.
        # FP64 garantiza que no habrá overflow/underflow catastrófico aquí.
        norm = jnp.linalg.norm(x, axis=-1, keepdims=keepdims)
        return jnp.maximum(norm, eps)
```

### 💀 FALLO NIVEL 5.1: La Gran Mentira de la Variedad de Stiefel $\mathrm{St}(D, k)$ (Traición Teórica)

**La Solución (Bulldog Fix - Implementación Real de SMW para Stiefel):**

```python
    @staticmethod
    @jax.jit
    def apply_stiefel_cayley_smw(X: jnp.ndarray, U: jnp.ndarray, V: jnp.ndarray, alpha: float = 1.0) -> jnp.ndarray:
        """
        Retracción Cayley-SMW REAL para la variedad de Stiefel St(D, k).
        X: (D, k), U: (D, 2k), V: (D, 2k).
        """
        eps = jnp.finfo(X.dtype).eps
        k = X.shape[-1]
        
        # 1. Construir la matriz de Woodbury M = I_{2k} + (alpha/2) * V^T U
        # V^T U es (2k, D) @ (D, 2k) = (2k, 2k)
        VtU = jnp.einsum('...ji,...jk->...ik', V, U) 
        I_2k = jnp.eye(2 * k, dtype=X.dtype)
        M = I_2k + (alpha / 2.0) * VtU
        
        # 2. Resolver el sistema lineal M * Z = V^T X  (Z será de 2k x k)
        # V^T X es (2k, D) @ (D, k) = (2k, k)
        VtX = jnp.einsum('...ji,...jk->...ik', V, X)
        
        # jnp.linalg.solve es estable y respeta la estructura de bloque
        Z = jnp.linalg.solve(M, VtX)
        
        # 3. Aplicar la retracción: Y = X - alpha * U * Z
        # U * Z es (D, 2k) @ (2k, k) = (D, k)
        Y = X - alpha * jnp.einsum('...ij,...jk->...ik', U, Z)
        
        # 4. Re-ortogonalizar con s-CholQR3 para garantizar que Y esté en St(D, k)
        # (La retracción de Cayley teóricamente preserva la ortogonalidad, 
        # pero en FP64 con alpha grande, el shift de Tikhonov lo hace robusto).
        return CliffordRotors.cholesky_qr3(Y)
```

```python
        """Desempaqueta y verifica criptográficamente un paquete PMTP v44."""
        if len(raw_packet) < 128:
            raise ValueError("PMTP Fatal: Packet smaller than 128 bytes.")

            raise PermissionError("PMTP Security: MAC verification FAILED. Packet rejected.")
            
        # 3. Desempaquetar header (usando el formato fix de 96 bytes del Nivel 2)
        # Asumiendo PMTP_HEADER_FMT = "<4s B B B Q 32s 32s Q Q d x"
        magic, ver, flags, shape_len, payload_bytes, sender_id, receiver_id, seq, reserved, ts = \
            struct.unpack(PMTP_HEADER_FMT, header_raw)
            
        if magic != PMTP_MAGIC:
            raise ValueError("PMTP Error: Invalid magic bytes.")
            
        # 4. Validación Anti-Replay (Tolerancia de 60 segundos exigida por el Whitebook)
        current_time = time.time()
        if abs(current_time - ts) > 60.0:
            raise PermissionError(f"PMTP Security: Timestamp drift > 60s. Replay attack suspected.")
            
        # 5. Validación Anti-DoS (Exigida por el Whitebook, faltaba en el código original)
        MAX_PAYLOAD = 100 * 1024 * 1024 # 100 MB
        if payload_bytes > MAX_PAYLOAD:
            raise MemoryError(f"PMTP Anti-DoS: Payload {payload_bytes} exceeds MAX_PAYLOAD {MAX_PAYLOAD}.")
            
        # 6. Validar que el payload real coincida con el declarado
        if len(payload) != payload_bytes:
            raise ValueError(f"PMTP Error: Declared payload {payload_bytes} != actual {len(payload)}.")

        return {
            "sender_id": sender_id, "receiver_id": receiver_id, "seq": seq, 
            "timestamp": ts, "shape_len": shape_len, "payload": payload
        }
```

### 💀 FALLO NIVEL 5.3: XLA Memory Bloat por `jnp.where` en `log_map` (Estrangulamiento de HBM)
**El Ataque:** En `log_map`, usas:
```python
return jnp.where(is_identity, jnp.zeros_like(x), log_normal)
```
**El Daño en el Silicio:** En XLA, `jnp.where` a menudo obliga al compilador a **materializar ambas ramas** (el tensor `zeros_like(x)` y el tensor `log_normal`) en la memoria HBM antes de seleccionar. En $D = 10,000$ y con *batching* (ej. batch size 256), estás allocando $256 \times 10,000 \times 8$ bytes dos veces innecesariamente. Esto fragmenta la HBM y causa *Out-Of-Memory* (OOM) en GPUs de 24GB (como la T4/4090) cuando el batch crece.

**La Solución (Bulldog Fix - Máscara Multiplicativa Fusionable):**
En lugar de `where`, usa multiplicación por una máscara booleana. XLA puede fusionar esto directamente en el kernel de escritura sin allocar el tensor de ceros.
```python
    @staticmethod
    @jax.jit
    def log_map(x: jnp.ndarray, y: jnp.ndarray, tau_geom: float = 1e-12) -> jnp.ndarray:
        # ... (cálculos de theta, u_tangent, etc. igual que en el parche del Nivel 3) ...
        
        log_normal = theta * u_tangent
        
        # FIX NIVEL 5: Reemplazar jnp.where por multiplicación de máscara.
        # (theta >= tau_geom) se convierte a 1.0 o 0.0. XLA fusiona esto en un solo kernel.
        mask = (theta >= tau_geom).astype(x.dtype)
        return log_normal * mask
```
