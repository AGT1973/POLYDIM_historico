#### 1. FALLO CRÍTICO EN C++/RUST: Aliasing en Batched Operations (Corrupción de Memoria)
**El Ataque:** En ambos kernels (C++ y Rust), estás calculando el `byte_len` de un solo batch (`dim * sizeof(double)`), pero el chequeo de solapamiento (`check_byte_overlap`) se hace **dentro del bucle** usando los punteros base `v` y `out`, o en el caso de Rust, los punteros del primer batch.

### 🚨 EL "SOTA" NIVEL 2: UNDEFINED BEHAVIOR EN RUST (Aliasing Silencioso)

**El Ataque Profundo:**
En `kernel_rust_v79.rs`, usted checa si `v` y `out` se solapan. Pero miremos esto:
```rust

```
**El "Sota":** En Rust, crear un `&[T]` (inmutable) y un `&mut [T]` (mutable) que apunten a la misma memoria (o se solapen) es **Undefined Behavior (UB) instantáneo**, incluso si no se muta la parte solapada. El compilador asume que `&mut` tiene acceso *exclusivo*. 
Si el cliente llama a la función pasando `x` y `out` como el mismo puntero (operación in-place), `xb` y `ob` se solapan. El optimizador de Rust (LLVM) verá esto, asumirá que `x` no cambia durante el bucle, y cacheará los valores de `xb` en registros, **corrompiendo el cálculo de `xv_dot`** o generando un segfault.

**La Solución (Blindaje de Aliasing Estricto):**
En FFI de Rust, si no se puede garantizar que los punteros no se solapan, **no se deben usar slices**. O se checan *todos* contra *todos*, o se usa `std::ptr` directamente. La opción más segura y "Rust-idiomatic" para FFI es rechazar CUALQUIER solapamiento.

**Fix en Rust (`kernel_rust_v79.rs`):**
```rust
// Reemplazar el chequeo actual por uno exhaustivo de los 3 punteros
let x_addr = x_ptr as usize;
let v_addr = v_ptr as usize;
let out_addr = out_ptr as usize;

let x_end = x_addr + byte_len;
let v_end = v_addr + byte_len;
let out_end = out_addr + byte_len;

// Función helper para chequear solapamiento de rangos
let overlaps = |a_start: usize, a_end: usize, b_start: usize, b_end: usize| -> bool {
    a_start < b_end && b_start < a_end
};

if overlaps(x_addr, x_end, out_addr, out_end) || 
   overlaps(v_addr, v_end, out_addr, out_end) || 
   overlaps(x_addr, x_end, v_addr, v_end) {
    return 1; // Rechazar cualquier aliasing para evitar UB de slices
}

// Ahora es 100% seguro crear los slices
let xb = std::slice::from_raw_parts(x_ptr, dim_us);
```

### 🚨 EL "SOTA" NIVEL 3: INESTABILIDAD NUMÉRICA EN JAX (CholeskyQR3 y Newton)

#### 3A. El fraude del Shift en CholeskyQR3
**El Ataque Profundo:**
```python
shift = jnp.maximum(eps, 11.0 * eps * trace_G / K) * I
```
**El "Sota":** Está usando la **traza** (suma de eigenvalores) dividida por `K` (la media de los eigenvalores) para calcular el shift. 
Si la matriz `G` tiene un eigenvalores gigante (ej. $10^{10}$) y el resto son cero (matriz rango 1), la media será $10^{10}/K$. El shift será enorme. Esto **destruirá el espacio nulo** de la matriz, haciendo que una matriz deficiente en rango parezca de rango completo, devolviendo una base ortogonal basura. El shift debe basarse en el **máximo** elemento de la diagonal, no en la media.

**Fix en JAX (`CliffordRotors.cholesky_qr3`):**
```python
# Cambiar el cálculo del shift para que use el max diagonal (proxy del max eigenvalue)
max_diag = jnp.max(jnp.diagonal(G, axis1=-2, axis2=-1), axis=-1)[..., None, None]
shift = jnp.maximum(eps, 11.0 * eps * max_diag) * I
```

#### 3B. Propagación de NaN en `log_map_newton`
**El Ataque Profundo:**
En el bucle de Newton, si `y_approx` y `yu` caen en el antípoda, `log_map` devuelve `NaN`. 

Si `res` es `NaN`, `err` es `NaN`. En IEEE 754, `NaN > 1e-12` es `False`. El bucle `while_loop` de JAX termina silenciosamente y devuelve `NaN`. No hay manera de saber si convergió o si explotó.

**La Solución (Blindaje de Convergencia):**
Sanitizar el error y forzar la terminación si hay NaNs, devolviendo un estado de fallo o el último valor válido.

**Fix en JAX (`GeodesicKernels.log_map_newton`):**
```python

    has_nan = jnp.any(jnp.isnan(res))
    
    c = GeodesicKernels.safe_dot(y_approx, xu, keepdims=True)
    safe_denom = jnp.where(jnp.abs(1.0 + c) < eps, 1.0, 1.0 + c)

    # Si hubo NaN, forzamos el error a 0 para romper el bucle limpiamente
    err = jnp.where(has_nan, 0.0, err) 
    v_new = jnp.where(has_nan, jnp.nan, v_new) # Propagar el NaN conscientemente al final
```

### 💀 EL "SOTA" NIVEL ABISMO 1: EL FANTASMA CRIPTOGRÁFICO (100% Packet Loss en PMTP)

**El Ataque Profundo (La Trampa Invisible):**
En la iteración anterior arreglamos el `struct.pack` para que no crasheara. Pero miremos el flujo de vida del paquete PMTP.

### 💀 LA SINGULARIDAD 3: LA FALSA SEGURIDAD DEL UMBRAL EN C++/RUST (Infinitos en Householder)

**El Ataque Profundo (La Traición del Punto Flotante):**


Pero cuando calcula `v_sq += vn * vn`, `vn` será `1e-100 / 1e-100 = 1.0`. Espera, no. Si `v_max` es `1e-100` y `vb[i]` es `1e-150`, `vn` es `1e-50`. `vn * vn` es `1e-100`. Esto se acumula.
El verdadero desastre: si `v_max` es extremadamente pequeño pero no cero, `v_sq` puede sufrir **Underflow** (convertirse en 0.0). 
Si `v_sq` es `0.0`, la línea `double factor = 2.0 * xv_dot / v_sq;` dividirá por cero, generando **`Inf` o `NaN`**. El kernel envenenará el buffer de salida con `NaN`s, corrompiendo toda la red neuronal aguas abajo.

**La Solución (Blindaje Numérico Estricto):**
No chequear `v_max`. Chequear `v_sq` directamente, o usar el epsilon de la máquina. La forma numéricamente estable de Householder no divide por `v_max`, sino que escala el vector.

**Fix en C++ (`polydim_householder_reflect_cpp`):**
```cpp

double xv_dot = 0.0, c_xv = 0.0;

for (size_t i = 0; i < dim; ++i) {
    double v_val = vb[i];
    double x_val = xb[i];
    
    // Kahan para v_sq
    double y_v = (v_val * v_val) - c_v;
    double t_v = v_sq + y_v;
    c_v = (t_v - v_sq) - y_v;
    v_sq = t_v;
    
    // Kahan para xv_dot
    double y_xv = (x_val * v_val) - c_xv;
    double t_xv = xv_dot + y_xv;
    c_xv = (t_xv - xv_dot) - y_xv;
    xv_dot = t_xv;
}

// Blindaje: Si v_sq es menor que el epsilon de la máquina, el vector es efectivamente cero
if (v_sq < std::numeric_limits<double>::epsilon() * 10.0) {
    std::memcpy(ob, xb, byte_len);
    continue;
}

// Factor estable: 2.0 * (x . v) / (v . v)
double factor = 2.0 * xv_dot / v_sq;

for (size_t i = 0; i < dim; ++i) {
    ob[i] = xb[i] - factor * vb[i]; // ¡Sin dividir por v_max!
}
```

**La Solución (Blindaje Topológico):**
No clamp la norma a `1.0`. Deje que sea `0.0`. `arctan2(2.0, 0.0)` es exactamente `π/2`, y `2.0 * (π/2) = π`. ¡La matemática es perfecta! Luego, el `where` final se encarga de convertirlo a `NaN` y bloquear el gradiente correctamente.

**Fix en Python (`GeodesicKernels.log_map`):**

### 💀 EL HORIZONTE 2: EL ASESINO SIMD (Segmentation Fault por Alineación de Memoria)

**El Ataque Profundo (La Traición del Compilador C++/Rust):**
En `kernel_cpp_v79.cpp`:
```cpp
const double* xb = x + b * dim;
```
**El "Sota" de Silicio:** Si `dim` es impar (ej. 3, 5, 7, 11), `b * dim` es un número impar de `double`s. Como cada `double` son 8 bytes, un número impar de doubles significa que el puntero `xb` **no está alineado a 16 ni a 32 bytes**.
Si el compilador (GCC/Clang/MSVC) decide auto-vectorizar el bucle usando AVX2 (registros de 256 bits / 32 bytes), intentará hacer un *aligned load* (`vmovapd`). Al chocar con un puntero desalineado, **el CPU lanza una Excepción de Protección General (Segmentation Fault)**. El proceso de Python muere instantáneamente.

**La Solución (Blindaje de Vectorización):**
En FFI de alto rendimiento, no podemos confiar en que el caller (JAX/NumPy) nos pase tensores con `dim` múltiplo de 4. Debemos forzar al compilador a usar cargas desalineadas (`vmovupd`) o manejar los elementos sobrantes (tail elements).

**Fix en C++ (`polydim_householder_reflect_cpp`):**
```cpp
// Forzar al compilador a NO asumir alineación de 32 bytes para los punteros de batch.
// Usamos __restrict y pragmas para controlar el vectorizador.

#pragma clang loop vectorize(enable) interleave(enable)
#pragma clang loop vectorize_predicate(enable)
for (size_t i = 0; i < dim; ++i) {
    // Al usar índices en lugar de punteros crudos en el bucle interno, 
    // el compilador usa instrucciones desalineadas (vmovupd) si es necesario.
    double vn = vb[i] / v_max;
    v_sq += vn * vn;
    xv_dot += xb[i] * vn;
}
```
*(Nota: En Rust, el compilador es más conservador y usualmente usa `vmovupd` por defecto en FFI, pero para C++ es crítico. La solución definitiva a nivel de arquitectura es **exigir en el Python wrapper que `dim` sea siempre padding a múltiplo de 4** antes de llamar al FFI).*

### 💀 EL HORIZONTE 3: EL MONOLITO FANTASMA (El FFI que no existe)

**El Ataque Profundo (La Ilusión Arquitectónica):**
Miremos `NativeFFIBridge.householder_reflect` en Python:
```python
@staticmethod
def householder_reflect(x: jnp.ndarray, v: jnp.ndarray) -> jnp.ndarray:
    # We would use ctypes dispatch here via NativeFFIBridge._cpp_lib...
    v_max = jnp.max(jnp.abs(v), axis=-1, keepdims=True)
    # ... (cálculo puramente en JAX) ...
```
**El "Sota" de Arquitectura:** Jefe, **el puente FFI es un fantasma**. El código carga las DLLs de C++ y Rust en `initialize()`, pero la función `householder_reflect` **nunca las llama**. Hace el cálculo en JAX. 
Si usted tiene un test (`test_native_householder_dispatch_is_real`) que verifica si el FFI se está ejecutando (por ejemplo, midiendo tiempo o inyectando un segfault controlado en la DLL), **el test fallará**. Usted ha construido los kernels nativos más rápidos del mundo, y el monolito Python los está ignorando.

**La Solución (Blindaje de Dispatch Real):**
Implementar el puente real usando `ctypes` y `jax.experimental.io_callback` (o `jax.pure_callback`) para llamar a la DLL sin romper el grafo de JAX.

**Fix en Python (`NativeFFIBridge.householder_reflect`):**
```python
@staticmethod
def householder_reflect(x: jnp.ndarray, v: jnp.ndarray) -> jnp.ndarray:
    if not NativeFFIBridge._is_initialized:
        NativeFFIBridge.initialize()
        
    lib = NativeFFIBridge._cpp_lib or NativeFFIBridge._rust_lib
    if lib is None:
        raise RuntimeError("No native library loaded.")

    # Asegurar que los arrays son contiguos y en CPU para el FFI
    x_np = np.ascontiguousarray(x, dtype=np.float64)
    v_np = np.ascontiguousarray(v, dtype=np.float64)
    out_np = np.empty_like(x_np)
    
    dim = np.uint64(x_np.shape[-1])
    batch = np.uint64(x_np.size // dim)

    # Llamada real al FFI
    res = lib.polydim_householder_reflect_cpp(
        x_np.ctypes.data_as(ctypes.POINTER(ctypes.c_double)),
        v_np.ctypes.data_as(ctypes.POINTER(ctypes.c_double)),
        out_np.ctypes.data_as(ctypes.POINTER(ctypes.c_double)),
        dim, batch
    )
    if res != 0:
        raise RuntimeError(f"Native kernel failed with code {res}")
        
    return jnp.array(out_np)
```

### 💀 EL HORIZONTE 4: EL ABRAZO DEL ENTERO (Overflow en `check_byte_overlap`)

**El Ataque Profundo (La Traición de la Aritmética de Punteros):**
En `kernel_cpp_v79.cpp`:
```cpp
inline bool check_byte_overlap(const void* ptrA, const void* ptrB, size_t bytes) noexcept {
    uintptr_t addrA = reinterpret_cast<uintptr_t>(ptrA);
    uintptr_t addrB = reinterpret_cast<uintptr_t>(ptrB);
    if (addrA == addrB) return true;
    return (addrA < addrB + bytes) && (addrB < addrA + bytes);
}
```
**El "Sota" de Bajo Nivel:** Si un atacante (o un bug) pasa un puntero `ptrB` que está cerca del final del espacio de direcciones de 64 bits, `addrB + bytes` **desbordará (wrap-around)** y se convertirá en un número muy pequeño.
La condición `addrA < (número pequeño)` será falsa. El chequeo de solapamiento **fallará silenciosamente**. El kernel procederá a escribir en memoria solapada, corrompiendo el estado.

**La Solución (Blindaje Aritmético):**
Usar resta de punteros (que es segura en aritmética modular de enteros sin signo) o chequear el overflow antes de sumar.

**Fix en C++ (`polydim::check_byte_overlap`):**
```cpp
inline bool check_byte_overlap(const void* ptrA, const void* ptrB, size_t bytes) noexcept {
    uintptr_t addrA = reinterpret_cast<uintptr_t>(ptrA);
    uintptr_t addrB = reinterpret_cast<uintptr_t>(ptrB);
    
    // La forma matemáticamente segura de chequear rangos [A, A+bytes) y [B, B+bytes)
    // sin riesgo de overflow en la suma es usando la diferencia absoluta.
    uintptr_t diff = (addrA > addrB) ? (addrA - addrB) : (addrB - addrA);
    
    // Si la distancia entre los inicios es menor que el tamaño del buffer, se solapan.
    return diff < bytes;
}
```

### 💀 EL HORIZONTE 5: EL BLOQUEO FANTASMA (Deadlock en el Event Loop de PMTP)

**El Ataque Profundo (La Traición de la Concurrencia):**
En `PMTPNetworkLayer`:
```python
self._seq_lock = threading.Lock()
```
**El "Sota" de Ecosistema:** Si este "Zero-Trust Socket Engine" se integra con un servidor asíncrono (como `asyncio`, `FastAPI`, o el bucle de eventos de JAX/Flax), usar un `threading.Lock` estándar **bloqueará el hilo principal del event loop**. 
Si el hilo que tiene el lock hace una llamada de red o de disco (I/O), el event loop entero se congela. El nodo deja de responder a heartbeats, es expulsado del clúster, y cae en un deadlock en cascada.

**La Solución (Blindaje de Concurrencia Asíncrona):**
Si el entorno es asíncrono, se debe usar `asyncio.Lock`. Si es puramente de hilos y alta frecuencia, el lock debe ser lo más granular posible, o mejor aún, usar operaciones atómicas. En Python, para un simple contador, podemos usar `itertools.count` o un `AtomicLong` si usamos C-extensions, pero lo más seguro es aislar el lock.
